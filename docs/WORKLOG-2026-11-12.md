## Resuming on another machine

1. Clone both repos side by side:
   ```
   git clone https://github.com/leo2m4a/pico_mst_260219.git
   git clone https://github.com/leo2m4a/pico_rx260101.git
   ```
2. In each repo, clone RadioLib as described in its README. It isn't committed.
3. Build with the Raspberry Pi Pico VS Code extension. The toolchain, SDK 2.2.0, ninja and picotool install under `~/.pico-sdk`.
4. The packet format spreadsheet is `docs/pico_lora_cmd2604091.ods` in both repos, and the two copies are identical. Open it with LibreOffice Calc. It has two sheets: the packet tables and **EEPROM**.
5. To flash a board: hold BOOTSEL, plug it in, then copy the `.uf2` from `build/` onto it, or run `picotool load -v -x build/<name>.uf2`. Connect **one board at a time** so the master and slave firmware don't get mixed up.

### UART EEPROM command (`0x83`)

| Byte | Write request | Read request |
|---|---|---|
| 0 | `0x83` | `0x83` |
| 1 | `0x10` | `0x08` |
| 4 | `0x11` | `0x35` |
| 5–6 | Word address (high, low) | Word address (high, low) |
| 7–14 | 8 data bytes | — |

Replies are 16 bytes, starting `0x92`, `0x10`, `0x02` (MID), `0x00`:

| Byte | Write reply | Read reply |
|---|---|---|
| 4 | `0x11` | `0x35` |
| 5 | Address high | `0x00` |
| 6 | Address low | data0 |
| 7–13 | data0–data6 | data1–data7 |
| 14 | data7 | `0x00` |
| 15 | `0x00` | `0x00` |

### EEPROM layout (AT24C32, I2C `0x57`, 32-byte pages)

| Address | Contents |
|---|---|
| `0x0000` | Reserved for system info. The size isn't defined in code; the sheet assumes 128 bytes, up to `0x0080` |
| `0x0080` | Default schedules, 96 bytes (`24 × 4`), loaded at startup with no check |
| `0x0100 + 0x20·n` | Relay n record, relays 0–3 (`0x0100`–`0x017F`) |

Relay record: `+0x00` schedule bytes 0–15, `+0x10` bytes 16–23, `+0x18`/`+0x19` signature `0x16`, `0x88`, `+0x1A` 6 bytes unused.

**To save relay n's schedule over UART**, send four `0x83` writes. These are relay 0's addresses; add `0x20·n` for relay n:

| Word address | Data |
|---|---|
| `0x0100` | Schedule bytes 0–7 |
| `0x0108` | Schedule bytes 8–15 |
| `0x0110` | Schedule bytes 16–23 |
| `0x0118` | `0x16`, `0x88`, then 6 unused bytes. Write this one **last** |

The new schedule takes effect at the next startup.

## Behaviour changes to check when testing

- **Host software:** after an address 4 relay write, the master now sends a 12-byte UART message starting `0x88`. Its relay handling never ran before, because reply byte 4 was `0`.
- **Host software:** the EEPROM read reply now has `0x35` in byte 4, no address, and data in bytes 6–13.
- **Master LCD:** after a poll, the length field shows `14` instead of `10`.
- **Master LCD:** the UART command debug output (result and length) is now on.
- **EEPROM:** anything written at `0x0010`–`0x004F` for the old per-relay layout is no longer read. Write it again at `0x0100` and above.

2. **Schedule sync from the master to the slave (recommended, not started).** The slave keeps `gSCH_RLY` in RAM only, so it loses it on reset, and nothing sends the master's saved schedules to it. The slave has no clock of its own and gets the time from the master's beacon, so the master should be the only place schedules are stored. Proposal:
   - Slave: put a checksum of its 24 schedule bytes in poll reply bytes 17–19 (currently `0xaa` padding).
   - Master: on each poll reply, compare it with the checksum of its saved schedule for that slave. If they differ, send the `0x10`/`0x11`/`0x12` writes and confirm each from its reply.
   - **Needs a decision first:** which of the master's schedule slots (relays 0–3) belongs to which slave SID? The master README lists `0x81` and `0x83`, but this slave is `0x84`.
